# Explicit WSGI Response Lifecycle and Preparation Contract

## Background

In Waitress, task execution couples WSGI response processing, HTTP header formatting, connection framing, and socket I/O into a single procedural flow. Key response states—including status codes, header lists, content length, chunked encoding flags, and connection closure decisions—are scattered across mutable task attributes. Methods like `build_response_header()` mutate `response_headers`, `close_on_finish`, and `chunked_response` in place, while channel socket transmission is deferred until `write()`.

Because response preparation directly alters task state, downstream embedders and diagnostic tools cannot inspect, serialize, or validate an outgoing HTTP response without mutating the task or advancing toward body emission. Furthermore, coupling framing decisions (such as keep-alive evaluation and chunked encoding selection) to mutable task state prevents testing response preparation independently of channel execution.

Waitress needs an explicit response model that separates response acceptance and serialization from task execution and channel I/O, providing a deterministic, inspectable response lifecycle while preserving existing WSGI and HTTP behavior.

## Goal

Make Waitress's WSGI response lifecycle an explicit, inspectable contract, separating response preparation and metadata handling from task execution and socket I/O while preserving all existing WSGI, HTTP, error, logging, and streaming semantics.

Key objectives:
- Expose prepared response state—including status, headers, framing decisions, and serialized head bytes—through an explicit, inspectable response object.
- Introduce a side-effect-free query to prepare and serialize the HTTP response head without performing channel I/O or mutating task state.
- Expose WSGI response acceptance as an accessible method on WSGI tasks, returning the standard body-writing callable.
- Maintain full backwards compatibility for existing task classes, legacy methods, observable attributes, error tasks, and wire-level behavior.

## Public contract to preserve

- `waitress.task` MUST expose an importable `PreparedResponse` type.
- `Task` MUST expose a no-argument `prepare_response()` method returning a `PreparedResponse` with the following publicly accessible properties:
  - `status`: the response status string (e.g., `"200 OK"`).
  - `version`: the effective HTTP version (`"1.0"` or `"1.1"`).
  - `header_bytes`: the complete serialized response head as `bytes`, ending with `\r\n\r\n`.
  - `headers`: an ordered tuple of normalized `(name, value)` string pairs in wire order.
  - `body_allowed`: boolean indicating whether the status code permits a message body.
  - `chunked`: boolean indicating whether chunked transfer framing is active (always `False` when `body_allowed` is `False`, and `False` when an effective content length is established; `True` for HTTP/1.1 body-permitting responses without an effective content length, whether `Transfer-Encoding` was preset or auto-selected).
  - `close_connection`: boolean indicating whether the connection must close after the response.
  - `content_length`: the effective outgoing integer content length, or `None` if no effective length is present:
    - A length of `0` is an effective content length and MUST be returned as integer `0` (not `None`).
    - When a message body is permitted, an explicit `Content-Length` header in response headers takes precedence over `Task.content_length` if both are present.
    - For status codes that forbid a message body (1xx, 204, 304), `content_length` MUST be `None`, even if an application or task pre-set an explicit `Content-Length` header or task content length.
- **String normalization for directly preset headers**: Ordinary header values directly pre-populated in `Task.response_headers` outside `WSGITask.start_response()` MUST be converted with `str(value)` when constructing the prepared header pairs. `PreparedResponse.headers` MUST contain actual string names and string values; converting values only while formatting `header_bytes` is insufficient. For example, with `task.content_length = 0` and `task.response_headers = [("X-Retry-Count", 3)]`, `prepare_response().headers` MUST contain `("X-Retry-Count", "3")`, and `header_bytes` MUST contain `b"X-Retry-Count: 3\r\n"`. This conversion MUST NOT mutate the original `Task.response_headers` during preparation. The special Content-Length parsing and no-body header suppression rules below still apply.
  - This normalization applies to direct task-header preparation only. `WSGITask.start_response()` MUST continue to reject non-string status, header names, and header values with `AssertionError`; it MUST NOT silently coerce those WSGI inputs.
- `prepare_response()` MUST be a side-effect-free query that performs no channel I/O and does not mutate task state (`response_headers`, `close_on_finish`, `chunked_response`, `wrote_header`, `content_bytes_written`, or warning latches). Repeated calls under unchanged task state MUST yield identical values and `header_bytes`.
- `WSGITask` MUST expose `start_response(status, headers, exc_info=None)` as an accessible method that accepts response metadata and returns the task's body-writing callable (`self.write`).
- Existing public classes and methods in `waitress.task` MUST remain available with compatible signatures and return types, including `Task`, `WSGITask`, `ErrorTask`, `service()`, `start()`, `execute()`, `finish()`, `write()`, `build_response_header()`, `set_close_on_finish()`, `remove_content_length_header()`, and `has_body`.
- Existing observable task attributes MUST remain compatible across the task lifecycle, including `status`, `version`, `response_headers`, `content_length`, `content_bytes_written`, `wrote_header`, `chunked_response`, `complete`, `close_on_finish`, `logged_write_excess`, and `logged_write_no_body`.
- The compatibility side effects of `build_response_header()` MUST preserve the legacy append order of the observable `Task.response_headers` list. This internal list order is distinct from wire order: `PreparedResponse.headers` and serialized `header_bytes` MUST still use the stable lexicographical header-name sorting specified below. Do not overwrite `Task.response_headers` with the sorted wire-order headers.
  - For an HTTP/1.1 `200 OK` response with no effective content length, initially empty `response_headers`, a non-empty configured server identity, and no pre-existing closure flag: if the request specifies `Connection: close`, `build_response_header()` MUST leave header names in exactly `Connection`, `Transfer-Encoding`, `Server`, `Date` order.
  - Under the same conditions, if the request has no `Connection` header, `build_response_header()` MUST leave header names in exactly `Transfer-Encoding`, `Connection`, `Server`, `Date` order.
- When evaluated on the same pre-emission response state (before `build_response_header()` or `write()` has mutated task state), `build_response_header()` MUST return bytes identical to the `header_bytes` produced by `prepare_response()`, while retaining its no-argument signature, bytes return value, and compatibility side effects.

## Behavior that must stay unchanged

- **WSGI response acceptance and validation**:
  - The `status` argument and all header names and values in `headers` passed to `start_response` MUST be strings; passing a non-string for any of these MUST raise `AssertionError`.
  - If `status`, any header name, or any header value contains carriage return (`\r`) or line feed (`\n`) characters, `start_response` MUST raise `ValueError`.
  - If `headers` contains any WSGI hop-by-hop header (case-insensitive match for `connection`, `keep-alive`, `proxy-authenticate`, `proxy-authorization`, `te`, `trailer`, `transfer-encoding`, or `upgrade`), `start_response` MUST raise `AssertionError`. This hop-by-hop restriction applies strictly to `WSGITask.start_response`; direct pre-population of `Task.response_headers` outside `start_response` is not evaluated under WSGI hop-by-hop rules.
  - Calling `start_response` a second time without `exc_info` after response metadata has already been accepted MUST raise `AssertionError` with the message `"start_response called a second time without providing exc_info."`.
  - Calling `start_response` with `exc_info` before response headers have been emitted MUST clear previously accepted response headers and update status and headers according to the new call, while other observable task attributes retain existing update semantics. If called after response headers have already been emitted, it MUST re-raise `exc_info[1]`.
  - A `Content-Length` header supplied in `headers` passed to `start_response` MUST establish the effective integer content length; values that cannot be parsed as integers MUST raise `ValueError`.

- **Response-head serialization and headers**:
  - Tasks initialized with unsupported HTTP request versions MUST fall back to HTTP/1.0. If a task's `version` is explicitly set to any value other than `"1.0"` or `"1.1"` prior to preparation, attempting to prepare headers MUST raise `AssertionError`.
  - Serialized response heads (`header_bytes`) MUST format the status line as `HTTP/<version> <status>`, apply canonical hyphenated title-casing to header names, sort headers lexicographically by normalized header name while preserving relative order for duplicate header names, and terminate with exactly one empty CRLF-delimited line (`\r\n\r\n`).
  - For status codes 1xx, 204, and 304, any `Content-Length` or `Transfer-Encoding` headers present in `Task.response_headers` MUST be omitted during header normalization and serialization without evaluating their value (`content_length` is forced to `None` and no `ValueError` is raised). For all other status codes where a message body is permitted, any `Content-Length` header directly preset in `Task.response_headers` (or accepted via `WSGITask.start_response()`) MUST establish the effective integer content length; values that cannot be parsed as integers MUST raise `ValueError` upon response preparation (`prepare_response()`, `build_response_header()`). Other headers directly preset in `Task.response_headers` (including `Transfer-Encoding`) fall under standard header preservation and MUST NOT be proactively stripped or filtered, maintaining backward compatibility with direct task header usage.
  - For `Date`: all supplied `Date` headers (including empty-valued and duplicate headers) MUST be preserved in the response head in their original relative declaration order. When evaluating whether to emit an auto-generated `Date` header, if `Date` is absent or its last occurrence in `response_headers` has an empty value, an auto-generated `Date` header formatted from the task's `start_time` in standard HTTP date format MUST be emitted (appended to `normalized_headers`, stably following preset `Date` headers upon lexicographical sorting in serialized output). If the last occurrence of `Date` has a non-empty value, no generated `Date` header is added.
  - For `Server` and `Via`: all supplied `Server` headers (including empty-valued and duplicate headers) MUST be preserved in the response head in their original relative declaration order. Evaluation of whether `Server` is empty or non-empty is determined by its last occurrence in `response_headers`:
    - If the last occurrence of `Server` has a non-empty value, a `Via` header MUST be emitted containing the configured server identity (`adj.ident`), or `"waitress"` if `adj.ident` is empty or None (appended to `normalized_headers`), and no generated `Server` header is added.
    - If `Server` is absent or its last occurrence has an empty value, a `Via` header MUST NOT be added; instead, if `adj.ident` is non-empty, an auto-generated `Server` header containing `adj.ident` MUST be emitted (appended to `normalized_headers` before `Date`, stably following preset `Server` headers upon lexicographical sorting in serialized output; if `adj.ident` is empty or None, no generated `Server` header is added).

- **Connection framing and body eligibility**:
  - For HTTP/1.0 responses, keep-alive MUST only be established when the request's `Connection` header value equals `keep-alive` case-insensitively AND an effective content length is present (including `0`), provided the connection has not already been marked for closure (e.g., via pre-existing `close_on_finish=True` or on an `ErrorTask`). When keep-alive is established, `Connection: Keep-Alive` MUST be emitted (deduplicating to exactly one `Connection: Keep-Alive` if already present in `response_headers`), and the connection MUST NOT be marked to close (`close_connection=False` and `close_on_finish=False`). In all other cases (e.g., absent or non-keep-alive request header, missing content length, pre-existing `close_on_finish=True`, or on an `ErrorTask`), mandatory connection closure takes precedence: keep-alive MUST NOT be established, the connection MUST remain marked for closure (`close_connection=True` and `close_on_finish=True`), and exactly one `Connection: close` MUST be emitted on wire output (superseding and replacing any conflicting preset header such as `Connection: Keep-Alive`, and deduplicating if `Connection: close` is already preset).
  - For HTTP/1.1 responses, mandatory closure is triggered when the incoming request specifies `Connection: close`, when the task has `close_on_finish=True`, when the task is an `ErrorTask`, or when no effective content length is established on a body-permitting response (requiring chunked framing). In all such mandatory closure cases, the connection MUST be marked for closure (`close_connection=True` and `close_on_finish=True`), and exactly one `Connection: close` MUST be emitted on wire output (superseding and replacing any conflicting preset header such as `Connection: Keep-Alive`, and deduplicating if `Connection: close` is already preset). Conversely, for clean HTTP/1.1 responses where an effective content length is established and no closure condition exists, persistent connection is default (`close_connection=False` and `close_on_finish=False`), no `Connection` header is automatically appended, and non-conflicting preset headers are preserved.
  - For HTTP/1.1 responses where the response permits a body and no effective content length is established, chunked transfer framing MUST be selected (`chunked=True`), and the connection MUST be marked for closure upon completion (`close_connection=True` and `close_on_finish=True`, emitting `Connection: close`). The interaction between directly preset `Transfer-Encoding` headers, automatic chunked framing selection, and wire emission is defined as follows:
    - **Absent preset `Transfer-Encoding`**: an auto-generated `Transfer-Encoding: chunked` header MUST be emitted (`chunked=True`).
    - **Preset non-chunked `Transfer-Encoding`** (e.g. `Transfer-Encoding: gzip`, `deflate`): the preset header MUST be preserved, AND an auto-generated `Transfer-Encoding: chunked` header MUST be **appended** stably following the preset header (`chunked=True`, not replacing the preset header and not merely setting a flag). In the serialized response head (`header_bytes` and `headers`), both headers are emitted in order (`Transfer-Encoding: gzip` followed by `Transfer-Encoding: chunked`), ensuring that `chunked` is the final transfer coding applied to the payload per RFC 7230 §3.3.1.
    - **Preset `Transfer-Encoding` with `chunked`** (e.g. `Transfer-Encoding: chunked`, case-insensitively): `chunked=True`, and the preset header already fulfills the chunked framing requirement; no second or duplicate `Transfer-Encoding: chunked` header is added (deduplicating to a single `Transfer-Encoding: chunked` header on wire output per RFC 7230 §3.3.1).
    - When `chunked=True`, wire body output written to the channel MUST be framed with chunk lengths in uppercase hexadecimal followed by CRLF, payload bytes, CRLF, and terminal `0\r\n\r\n` upon task finish.
  - Conversely, when an effective content length IS established on a body-permitting response (via explicit `Content-Length` header or task content length), framing is length-delimited: `chunked=False`, no `Transfer-Encoding: chunked` header is generated, and any preset `Transfer-Encoding` header (e.g. `Transfer-Encoding: gzip`) is preserved as-is on wire output alongside the `Content-Length` header, with the body emitted raw without chunk framing.
  - For HTTP/1.0 responses, chunked transfer framing is not supported (RFC 7230 §3.3.1): chunked framing is always disabled (`chunked=False`), an auto-generated `Transfer-Encoding: chunked` header is NEVER added by the server, and the response body is always emitted raw without chunk encoding. Any headers directly preset in `Task.response_headers` (including preset `Transfer-Encoding` headers such as `gzip` or `chunked`) are preserved as-is on wire output under standard header preservation rules for body-permitting status codes (unless stripped under Tier 1 for no-body status codes 1xx, 204, 304). Furthermore, when an HTTP/1.0 response lacks an effective content length, or whenever keep-alive negotiation conditions defined above are not satisfied, mandatory connection closure applies (`close_connection=True`, emitting `Connection: close`).
  - Responses with status codes 1xx, 204, or 304 MUST forbid a message body (`body_allowed=False`), MUST NOT enable chunked transfer framing (`chunked=False`), and MUST NOT emit `Content-Length` or `Transfer-Encoding` headers in `header_bytes` or `headers`. This requirement strictly overrides header preservation: if `Content-Length` or `Transfer-Encoding` headers were directly present in `Task.response_headers`, they MUST be omitted from the prepared headers and serialized head bytes.
  - Except for the explicit compatibility exceptions defined below, emitted framing headers (`Connection`, `Content-Length`, `Transfer-Encoding`, `Date`, `Server`, `Via`) MUST remain byte-for-byte compatible in presence, values, and ordering with existing Waitress output for equivalent states.

- **Compatibility exceptions, decision matrix, and rule precedence**:
  - **Compatibility Exceptions**: While response preparation and framing preserve byte-for-byte fidelity with existing Waitress output across standard states, the following specific behaviors are intentional compatibility exceptions and contract refinements where RFC compliance, input validation, and connection lifecycle safety take precedence over legacy baseline byte preservation:
    1. *No-body Transfer-Encoding and Content-Length suppression*: Legacy Waitress only stripped `Content-Length` for 1xx, 204, and 304 responses, leaking any directly preset `Transfer-Encoding` into wire output. Under the explicit model, RFC 7230 §3.3.1 strictly forbids `Transfer-Encoding` on responses that forbid a body: any preset `Transfer-Encoding` (and `Content-Length`) MUST be stripped, `chunked` is forced to `False`, and `content_length` is forced to `None`.
    2. *Mandatory connection closure precedence (HTTP/1.0 & HTTP/1.1)*: Legacy Waitress evaluated keep-alive without enforcing server-side closure invariants, improperly negotiating keep-alive on HTTP/1.0 even when `close_on_finish=True` or on an `ErrorTask`, and improperly leaking conflicting preset `Connection: Keep-Alive` headers into wire output before closing the socket on both HTTP/1.0 and HTTP/1.1. Under the explicit model, mandatory closure strictly supersedes client keep-alive negotiation and conflicting preset `Connection` headers across both HTTP/1.0 and HTTP/1.1: keep-alive MUST NOT be established, `close_connection` and `close_on_finish` MUST be `True`, conflicting preset headers (such as `Connection: Keep-Alive`) MUST be replaced with `Connection: close`, and exactly one `Connection: close` header MUST be emitted on the wire.
    3. *Duplicate Transfer-Encoding: chunked deduplication*: Legacy Waitress emitted duplicate `Transfer-Encoding: chunked` headers when chunked was already preset in response headers and auto-selected for body-permitting HTTP/1.1 responses lacking content length. Under RFC 7230 §3.3.1, multiple chunked transfer codings are prohibited; prepared output deduplicates to a single `Transfer-Encoding: chunked` header on wire output.
    4. *Directly preset non-integer Content-Length validation*: Legacy Waitress did not validate directly preset `Content-Length` header values in `Task.response_headers`, leaking malformed or unparseable values into wire output. Under the explicit model, any non-integer `Content-Length` value on body-permitting responses strictly raises `ValueError` upon preparation (`prepare_response()`, `build_response_header()`).
    5. *Explicit Content-Length header precedence for body emission and excess truncation*: Legacy Waitress evaluated body truncation and excess content warning against `Task.content_length`, which conflicted with explicit `Content-Length` headers directly supplied by applications. Under the explicit model, an explicit `Content-Length` header takes precedence over task attributes for both header serialization and wire-level body emission (emitting wire body bytes conforming to the declared header length and truncating excess bytes against that header).

  - **Rule Precedence Hierarchy**:
    1. **Tier 1 — RFC Protocol Prohibitions (Top Priority)**: For status codes forbidding a body (1xx, 204, 304), `body_allowed=False`, `chunked=False`, `content_length=None`. `Content-Length` and `Transfer-Encoding` MUST NEVER be emitted in `headers` or `header_bytes`, strictly superseding header preservation.
    2. **Tier 2 — Mandatory Connection Closure Precedence**: Whenever mandatory closure is in effect (`close_on_finish=True`, `ErrorTask`, client `Connection: close`, chunked response without length, or HTTP/1.0 without keep-alive negotiation), mandatory closure strictly supersedes client keep-alive requests AND overrides any conflicting preset `Connection` headers (such as `Connection: Keep-Alive`) on both HTTP/1.0 and HTTP/1.1 (`close_connection=True` and `close_on_finish=True`, emitting exactly one `Connection: close`).
    3. **Tier 3 — Explicit Header Precedence**: When a message body is permitted, an explicit `Content-Length` header in `response_headers` takes precedence over `Task.content_length` (including `Content-Length: 0` over non-zero `Task.content_length`) for both header preparation and wire-level body emission (emitting wire body bytes conforming to the declared header length). Values that cannot be parsed as integers MUST raise `ValueError` upon preparation.
    4. **Tier 4 — Standard Wire Compatibility and Header Preservation (Default)**: In all scenarios where Tiers 1–3 do not mandate specific overrides, emitted framing headers (`Connection`, `Content-Length`, `Transfer-Encoding`, `Date`, `Server`, `Via`), custom headers, and wire-level byte ordering MUST remain byte-for-byte identical to legacy Waitress output for equivalent states. When HTTP/1.1 body-permitting responses lack an effective content length, chunked framing (`chunked=True`) appends `Transfer-Encoding: chunked` to any preset non-chunked `Transfer-Encoding` header (preserving both in stable order) or deduplicates to a single `Transfer-Encoding: chunked` if already preset.

- **Body emission, framing, and warning state**:
  - Calling `write()` before `start_response` has been called MUST raise `RuntimeError` with the message `"start_response was not called before body written"`.
  - The complete serialized response head MUST be written to the channel exactly once before any body bytes are emitted.
  - When chunked transfer encoding is active, body data written to the channel MUST encode chunk sizes in uppercase hexadecimal followed by CRLF (`\r\n`), the payload bytes, and CRLF. Calling `finish()` on a chunked task MUST emit the terminal chunk `b"0\r\n\r\n"`.
  - Body data written in excess of the declared `Content-Length` MUST be truncated to the remaining allowed bytes (adhering to the effective explicit header length when header precedence applies, emitting wire body bytes conforming to the declared header length), and an excess-content warning MUST be logged at most once (`logged_write_excess`).
  - For response statuses that forbid a message body (1xx, 204, 304), data passed to `write()` MUST NOT be emitted to the channel; the task's `content_bytes_written` counter MUST still track the ignored bytes, and an ignored-body warning MUST be logged at most once (`logged_write_no_body`).
  - When an application iterable finishes after producing fewer bytes than declared by `Content-Length`, non-HEAD responses MUST set `close_on_finish=True` and log a shortfall warning. For HEAD requests, returning fewer bytes than `Content-Length` MUST NOT set `close_on_finish` and MUST NOT log this warning.

- **Application iterables, file buffers, and cleanup**:
  - When no content length has already been established on the task, an iterable whose reported length is exactly one MUST infer the content length from its sole item, including an empty item whose inferred length is 0. If a content length has already been established, if the reported length is not exactly one, or if the iterable does not expose a length, this inference MUST NOT be performed.
  - When an application returns a file-wrapper buffer (`ReadOnlyFileBasedBuffer`) whose prepared size is non-zero, the effective content length MUST be reconciled with that size (updating `content_length` and replacing or removing mismatched headers), response headers MUST be emitted, and buffer ownership MUST be transferred to the channel via `write_soon(app_iter)` so that the task avoids closing the file in its `finally` block before channel consumption; the underlying file resource is closed once response consumption finishes (unless delegation fails, in which case the task remains responsible for cleanup in its `finally` block). When the prepared size is zero, the response MUST fall back to standard iterable handling and the buffer MUST be closed upon task completion.
  - For all other closeable iterables providing a `close()` method, `close()` MUST be invoked exactly once upon task completion across all normal and error paths.

- **Error tasks and socket error handling**:
  - `ErrorTask` instances MUST follow the unified response lifecycle, preserving their status code, generated body, `Content-Type: text/plain; charset=utf-8`, content length, server identity, and mandatory connection closure (`close_on_finish=True` and `close_connection=True` with `Connection: close`) across both HTTP/1.0 and HTTP/1.1 requests. Mandatory closure for `ErrorTask` strictly takes precedence over any client keep-alive request or preset `Connection` header (keep-alive MUST NOT be established, any conflicting preset header such as `Connection: Keep-Alive` is replaced with `Connection: close`, and exactly one `Connection: close` is emitted).
  - When an `OSError` occurs during task servicing (`service()`), `close_on_finish` MUST be set to `True`; if `channel.adj.log_socket_errors` is true, the `OSError` MUST be re-raised; if false, it MUST NOT be re-raised and task servicing MUST conclude cleanly.
