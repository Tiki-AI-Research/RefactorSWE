## Background
The docked and modal date picker variants each implement their own copy of the same month and year selection interaction: stepping months from the chevrons, toggling the month/year list menu with its rotation, scale, opacity and layout adjustments, and the list rows that represent selectable months and years. Because the two variant lines run in parallel and share only a common picker base, every adjustment to this interaction must currently be made twice, and the copies have already started to diverge in structure and in how the menu's open state is tracked. The duplication is accidental rather than a feature: one shared implementation of the selection interaction should serve both lines so that future fixes cannot diverge, while everything users observe through the pickers stays exactly as it is today.

## Goal
- Remove the duplicated month/year selection interaction so a single shared implementation serves the docked and modal picker lines, without changing anything observable from outside the pickers.
- Keep all existing month navigation, month/year list selection, menu open/close animation, year-bound enforcement and selection-event behaviour intact for both variants, including the input-based variant derived from the same picker base.
- Keep every existing public class, property, method, event, error type and declarative name usable exactly as it is, so no application built on these pickers has to change.
- Leave the internal structure free: how the shared behaviour is organized, where helpers live and which private state is used are implementation choices, as long as the contract below holds.

## Public contract to preserve
- `MDBaseDatePicker`, `MDDockedDatePicker`, `MDModalDatePicker` and `MDModalInputDatePicker` remain importable under their current names, and the selection container and list item classes addressed from the declarative layouts keep their current class names and view keys.
- `change_month(operation: str) -> None` keeps its string flag: `"next"` advances exactly one month and `"prev"` steps back exactly one month, wrapping across year boundaries with the year clamped so that it never drops below 1; it dispatches `on_select_month` with the resulting 1-based month number, and any other flag value keeps stepping backward as it does today.
- `update_calendar(year, month)` keeps accepting the target year and month numbers and refreshing the displayed calendar and its selection-derived label, without emitting selection events itself.
- `min_year` and `max_year` keep their current numeric defaults (1914 and 2121) and their role as bounds for the existing year-chevron navigation and year lists; moving a year chevron outside the inclusive range raises the module's public error `MDDatePickerTypeDateError` instead of clamping or applying the change. Month stepping does not use these bounds and keeps the year-1 clamp described above.
- The picker event surface (`on_select_day`, `on_select_month`, `on_select_year`, `on_dismiss`, `on_cancel`, `on_ok`, `on_edit`) and the selection containers' `on_release` and `on_open_menu` events remain dispatchable with the same payloads: `on_release` receives `"prev"` or `"next"`, while month and year selections receive integer values. `on_open()` remains the existing opening/motion method, not a registered event to dispatch. The base selection container keeps its variadic no-op `on_release(*args)` handler; concrete chevrons receive the direction flag.
- `get_date()` keeps returning a list of `datetime.date` values, and `set_text_full_date()` keeps returning its current formatted strings for every selection mode.
- Internal helpers, base types, private flags and widget composition may be reorganized freely; only the items above are fixed.

## Behavior that must stay unchanged
- Month stepping MUST behave identically on both variant lines: releasing a chevron with `prev` or `next` moves the displayed month by one, wrapping December to January and January to December across the year, refreshes the existing labels from their original date sources (selection-derived labels remain selection-derived), restores the calendar layout padding and fade-in as today, and emits exactly one `on_select_month` carrying the new 1-based month; stepping next and then prev from the same date MUST return the picker to the original month and year.
- The month/year menu toggle MUST keep its current visual contract: opening rotates the menu icon to -90 degrees, sets the calendar and chevrons to opacity 0 with disabled state and calendar scale 1.1, and expands the selection area (full available space for the docked variant, calendar width minus 36dp for the modal variant) with the existing animations; closing restores icon rotation 0, calendar opacity and scale 1, re-enables the calendar, collapses the selection area to zero size and restores the list scale as before.
- Year bounds MUST be enforced as today: the year lists offer the years from `min_year` up to but not including `max_year`; stepping the year chevron beyond either bound raises `MDDatePickerTypeDateError` and MUST NOT change the displayed calendar.
- Selecting a month row MUST apply the currently displayed year with the chosen 1-based month, dispatch `on_select_month` with that month number and mark the row selected; selecting a year row MUST apply the chosen year with the displayed month on the docked variant and with the selected-date month on the modal variant, dispatch `on_select_year` with that integer year and mark the row selected; the list data's `selected` flag MUST track the row's selected state, and a single touch MUST emit at most one such event.
- Repeated menu-toggle events MUST alternate open and closed as before. Preserve the separate existing direct-show API behavior: a direct `open_close_menu_month_year_selection(state=True)` call on a fresh docked picker does not advance its toggle state, so the first subsequent menu-toggle event still shows the list and the next closes it. Do not opportunistically synchronize these two entrypoints.
- `MDModalInputDatePicker` MUST continue to open, validate manually entered dates and honour its `date_format` options exactly as before.

## constraints
1. MUST NOT rename, remove or narrow any public class, property, method, event or error named above, and MUST NOT change their signatures, argument meanings or defaults.
2. MUST NOT change observable behaviour, animation parameters, durations, timing or event payloads; this is a behaviour-preserving restructuring with no new features and no opportunistic fixes.
3. MUST NOT add runtime dependencies or imports beyond the libraries these pickers already use.
4. MUST NOT change the declarative layout identifiers or the list data keys that the month and year selections rely on.
5. Keep the change confined to the production code needed to share the month/year selection interaction, plus only the minimal test adjustments the restructuring strictly requires; do not modify unrelated components, documentation, formatting or generated files.
