# Spec
`pdoc.render` stores rendering configuration in shared, module-level mutable template state: `pdoc.render.configure()` rewrites globals in that environment whenever configuration is updated, and the HTML renderer, the built-in web server, and the CLI all read these states implicitly. This is not merely an issue of where configuration lives: the server silently picks up whatever configuration was set last, the CLI must configure before starting, and cache invalidation must treat the rendering module specially to avoid losing configuration. Consequently, the behavior of each consumer depends on when another component mutated the shared state, making configuration impossible to reason about or test per consumer.

However, eliminating the internal reliance on shared configuration does not mean removing existing public interfaces. Users must still be able to call `pdoc.render.configure()` first and subsequently render through public entry points; custom filters and globals added to `pdoc.render.env` must also continue to take effect. Server configuration, meanwhile, must be isolated per instance: each instance uses the configuration in effect when it was created, and subsequent configuration changes must not affect an already-created server.

Separate rendering configuration from shared mutable global state so each consumer explicitly receives its required configuration, removing dependence on the configuration order of other components or implicitly reading their state. Preserve existing public configuration entry points, rendering entry points, and user-added template filters and globals so existing integrations require no changes. Configuration isolation only alters how configuration is held and passed, not the rendering output for a given configuration: for identical configurations, all rendered artifacts, static exports, and server responses must remain byte-identical to the current implementation, and CLI and HTTP contracts must remain unchanged, ensuring this change is a behavior-preserving refactor rather than a feature addition.

# Acceptance criteria
## Public contract to preserve
- `pdoc.render.configure` remains a keyword-only entry point returning `None`, whose configuration applies to subsequent public rendering calls. Parameters and default values remain unchanged: `docformat="restructuredtext"` (options: `"markdown"`, `"google"`, `"numpy"`, `"restructuredtext"`), `include_undocumented=True`, `edit_url_map=None` (treated as an empty mapping), `favicon=None`, `footer_text=""`, `logo=None`, `logo_link=None`, `math=False`, `mermaid=False`, `search=True`, `show_source=True`, `template_directory=None`.
- `pdoc.render.env` remains a module-level mutable Jinja2 environment where user-added filters and globals must take effect in subsequent renders; when the module cache is invalidated, the environment object's identity and its configured state must remain intact. Directly overwriting configuration values managed by `configure` is not guaranteed as part of backward compatibility.
- Module-level rendering entry points for module pages, the index page, error pages, the search index, and `repr` retain their names, parameters, and `str` return values (including the optional live-reload modification-time parameter for module rendering), rendering with the currently active configuration.
- `pdoc(*modules, output_directory=None)` continues to apply options via prior configuration; when no output directory is specified, it returns the first module's documentation string, otherwise writing each module page, index, and search artifacts (when enabled) into that directory and returning `None`.
- The CLI retains existing flags and semantics: output directory, docformat, edit URL mapping, favicon/logo/footer, math/mermaid, search/show-source, template directory, host, port, and browser-opening behavior.
- HTTP routes remain unchanged: `/` and `/index.html` serve the index, `/search.js` serves the search index, module paths serve module pages, and `?mtime=1` returns the modification time; unknown modules return `404` HTML, and exceptions caught by the baseline module import/render branch return `500` HTML, retaining original content types and error page content. Index and search-index rendering, and failures outside that branch, retain the baseline exception behavior; this refactor does not expand the scope of HTTP 500 handling.

## Behavior that must stay unchanged and implementation boundaries
- Under identical configurations and fixed inputs, all rendered outputs, static exports, and web responses must remain byte-identical to the current implementation, including when search is disabled, custom logo, footer, or template directory are used, and undocumented members are excluded; template autoescaping must remain in effect. Compare the same module source, templates, runtime, configuration and request. Supply identical mtime and error-detail inputs when comparing those outputs; their existing HTTP behavior and contents remain required.
- The server must render with the configuration in effect at creation time, continuing to support configuration prior to startup; subsequent configuration changes must not affect already-created instances. For configure(A) -> create Server A -> configure(B) -> request Server A, Server A uses A; a newly created Server B and direct public render calls use B. Compare Server A output against the baseline configured as A for the same fixed request, and compare Server B/direct output against the baseline configured as B. This clarifies the existing instance-isolation requirement without exempting stable response bytes.
- The search index must be computed only once per server instance and reused across requests; modules that fail to import must be skipped with a warning without failing the response. When search is disabled, the index must be empty, and static export must not write search index artifacts.
- The internal shape of the configuration carrier, its field layout, and the way consumers obtain it may be adjusted freely, provided the aforementioned contracts and behavioral requirements are met.

## Constraints
Constraints
1. Do not remove, rename, or narrow any public capability listed above, including parameter names, defaults, CLI flags, return shapes, output artifacts, HTTP routes, and status codes.
2. Do not change rendering semantics or output: no new options, template behavior, escaping rules, caching behavior, or server response content may be introduced; except where explicitly stated above, behavior must not depend on import or configuration order.
3. Do not add third-party dependencies or raise runtime requirements; changes must remain compatible with existing dependency constraints and Python version constraints.
4. Do not perform unrelated refactoring, renaming, or broad formatting churn, and do not modify public APIs beyond what is required for this task.
5. Scope of changes is strictly limited to production code, tests, and supporting adjustments necessary to make rendering configuration explicit; nothing else may be touched.
