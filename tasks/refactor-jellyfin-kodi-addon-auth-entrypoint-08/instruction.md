# Centralize stored connection loading

Three authentication entry paths independently load the addon data file and inject the first server's credentials, while every item helper rereads it for path mappings. Move loading and injection into the communication layer's configuration/credential component, reusing the existing stored-credential accessor's semantics. Load once and expose one injection entry point; remove the four duplicate reads and per-item disk access. Internal placement, cache strategy, and helper shape are yours to choose.

Before the first authenticated request, populate the already-resolved requested-server client's `api_client.config.data`: first stored server `address`, `Name`, `UserId`, and `AccessToken` map respectively to `auth.server`, `auth.server-name`, `auth.user_id`, and `auth.token`. Missing fields become `None`. `Actions(server_id=None, api_client=None)` remains constructible without arguments or with only server id; without a client, resolve one and inject configuration before reading its `auth.server`. `API(item, server=None)` retains one/two-argument construction and optional artwork-server behavior.

The item helper obtains first-server `paths` from loaded configuration, defaulting to an empty mapping when that stored server has no `paths` field. Preserve existing substring replacement: configured mapping keys can match anywhere in the path, not only at its beginning. When no mapping key matches, the replacement step leaves the path unchanged; preserve existing path preprocessing. The existing accessor remains available to connection setup, path settings, and logging, with `Servers` defaulting to an empty list. It remains their only stored-file reader; do not duplicate loading or normalization elsewhere.

Preserve caller-specific failures. Playback entry, playback actions, and item helper retain the existing `Addon appears to not be configured yet: ...` warning for missing/unreadable data or no servers, without new exceptions or visible output. Playback actions continue using the client's existing server value when loading fails. Context-menu file-open failure still propagates because that read is currently unguarded; do not turn it into a warning. If its file opens but has no servers, retain warning-and-continue behavior. Item construction must neither raise for absent data/servers nor access the stored file again per instance, including metadata checks after a failed load. Repairing pre-existing failures caused by an absent client server key or subsequent path resolution without a stored server is outside this refactor's scope.

Completion requires centralized loading/injection and configured path access, with directly relevant tests supporting credential timing/values, no-client construction, mappings, and differing unconfigured behavior. Reuse/cache must preserve values for a given configured addon during a run without delaying/skipping injection. Add no dependencies, settings, public strings, or caller-shape changes. Limit edits to necessary production code and directly related tests/support; avoid unrelated refactors, renames, or formatting.

Work in a new branch from `main` and commit the completed changes.
